## Objective and product context

Review and improve `packages/express-oidc-vault`'s DPoP implementation and `packages/oidc-vault-dpop-client`, then implement and independently verify every task below. The product keeps upstream OIDC refresh/ID tokens server-side, authenticates browser login with a temporary transaction cookie, binds vault exchange/refresh/logout and app-local API JWTs to one persistent browser key, and supports both tab-local body handles and shared HttpOnly cookie sessions. Ordinary business workflows include redirect/reload, session renewal during parallel API calls, explicit sign-out, network failure recovery, browser-key loss, and multiple APIs behind a gateway.

The review focuses on reliable sender-constrained authentication and a usable installed TypeScript package: consistent credential contracts, lifecycle isolation, bounded network work, nonce/error recovery, gateway scoping, key recovery, measured critical-path cost, and public declaration/documentation health.

### Task DPH-03: Bound vault HTTP work and honor API cancellation before side effects

Status: completed

Kind: defect

Priority: P1 — an unresolved response can hold refresh single-flight and a cookie Web Lock indefinitely; an already-aborted API call currently starts refresh.

Suggested agent: browser HTTP-resource implementer

Dependencies: DPH-02

Primary ownership:

- `packages/oidc-vault-dpop-client/src/{auth-session,auth-fetch,errors}.ts` and an internal HTTP/abort helper.
- Focused stalled-transport/body/cancellation tests and README/JSDoc.

Finding and references:

- Vault `post` (`auth-session.ts:191-231`) awaits fetch and unbounded `response.json()` without a deadline. `refreshPromise` and cookie locks wait for it.
- API fetch (`auth-fetch.ts:122-128`) refreshes before checking `signal.aborted`; retry branches (`:168,173`) await response cancellation, which can itself reject or never settle.

Requirements:

1. Add validated session options for a finite per-attempt header-plus-body request deadline (default 15,000 ms) and a maximum vault response size (default 1 MiB). Bound actual streamed bytes, not just Content-Length, and retain the deadline until parsing completes. Expose units/defaults in declarations and README.
2. Abort session-owned in-flight HTTP work on disposal. Race against a deadline even when an injected fetch/stream ignores AbortSignal. Cleanup is best effort and cannot replace the primary error or delay settlement indefinitely.
3. Check an API caller's existing AbortSignal before any refresh/key/sign/network work and when awaiting refresh/key work; aborting one caller must not cancel another caller's shared session refresh. Stop further retries promptly.
4. Keep fixed client errors, credentials/redirect/no-store policy, fresh proofs per permitted attempt, and no automatic retry of network/timeout failures. Document the uncertain-server-commit consequence of a lost mutation response.
5. Integrate `SessionAuthority.signal` with per-attempt transport abortion on clear/invalidation as well as disposal, preserving immediate local authority, FIFO/cookie single-flight, and late-publication/navigation guards. Preserve malformed-JSON response handling while allowing resource-bound errors to propagate; observe late fetch/read/cancel rejections and cancel late responses best effort. API caller cancellation must also stop continuation after proof/network waits, and retry-response cleanup must neither stall retries nor replace their primary outcome.
6. Implementation finding: `src/dpop-proof.ts` awaits the access-token digest before signing, so checking only around `createDpopProof` would still allow a new signature after cancellation during that digest. Own the narrow proof-helper/test change to accept an optional documented `DpopProofInput.signal`, check it before crypto and after the digest, and stop waiting on already-started crypto without claiming to cancel Web Crypto itself.

Acceptance criteria:

- Never-resolving fetch, stalled/trickled/oversized JSON, incorrect Content-Length, rejecting/never-resolving cancellation, and disposed in-flight work settle within the configured bound without unhandled rejection.
- A pre-aborted API invocation makes zero refresh/key/network calls; abort during shared refresh cancels only that wait and no later API attempt.
- A failed attempt releases the client queue/refresh ownership so subsequent explicit operations can proceed; nonce retry count remains bounded.
