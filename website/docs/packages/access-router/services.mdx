# Services

Routers expose service access for custom routes and tests.

## Model Router Services

`ModelRouter.getService(req)` returns the internal model service.
`ModelRouter.getPublicService(req)` returns the public wrapper used by the built-in routes.

Common public methods:

- `_new()`
- `_list(filter, args?, options?)`
- `_read(id, args?, options?)`
- `_readFilter(filter, args?, options?)`
- `_create(data, args?, options?)`
- `_update(id, data, args?, options?)`
- `_upsert(data, args?, options?)`
- `_delete(id)`
- `_distinct(field, options?)`
- `_count(filter, access?)`

These methods are what the built-in HTTP routes call internally.

### Trusted per-call authorization

Internal `find`/`findOne`/`findById`, `updateOne`/`updateById` and `upsert` accept
`options.authorization` with independent `rows`, `outputFields` and `related`
dimensions. `create` accepts output/related only; `new` accepts output only and
continues to **ignore select**, including empty/exclusion selections. Standalone
`exists`/`count`/`delete`/`distinct` and dedicated subdocument operations retain their
request-policy APIs. Embedded output inside integrated parent/target results inherits
that model's field paths; a new `subdocuments` policy or input-field elevation is unsupported.

All authorization input is **trusted server-only**. Use `router.getService(req)` or
`req.macl.getService(...)` after the owning runtime's middleware initializes the request.
There is no standalone `Service` export. Root and `/advanced` expose the policy types
and opaque consumer handles, while issuers, resolved execution and prepared queries
remain private. The installed package README contains a complete runnable Mongo/Express
example and the full breaking-release migration table.

<!-- doc-example: partial -->

```ts
import type { ModelRouter, OutputAuthorization } from '@web-ts-toolkit/access-router';
import type { ModelRequest } from '@web-ts-toolkit/access-router/advanced';
type Order = { status?: string; internalNote?: string; tenantId: string };
declare const router: ModelRouter<Order>;
declare const req: ModelRequest;
declare const orderId: string;
declare const tenantId: string; // resolved by trusted server code
const service = router.getService(req);
const output = { outputFields: { mode: 'grant', paths: ['internalNote'] } } as const satisfies OutputAuthorization<Order>;
const result = await service.findOne(
  { _id: orderId },
  { select: ['status', 'internalNote'] },
  { skim: true, includePermissions: false, includeFieldPermissions: false,
    authorization: { ...output, rows: { mode: 'scope', filter: { tenantId } } } },
);
if (result.success) {
  const reuse = { documentAuthorization: result.context.documentAuthorization };
  const picked = await service.pickAllowedFields(result.data, 'read', reuse);
  await service.trimOutputFields(picked, 'read', reuse);
}
```

Business output is selected AND (request permission OR explicit grant). Grants are
additive: the stored selected note survives false/missing user rules, while denied
`status` is omitted. A granted-but-unselected note is omitted too. Missing values are
never fabricated or made required by a grant. Omitted select uses normal request fields
plus named grants; unrestricted uses the captured persisted/registered-virtual catalog.
Explicit exclusions and `requireExplicitSelect` still apply.

Grant paths use ordinary dotted response paths such as `contacts.email`, without
`sub` markers, signed tokens, indices or wildcards. Readonly path arrays are accepted.
Known model/virtual shapes are checked; unknown models use a runtime-validated string
fallback. A container grants its selected eligible subtree; a leaf grants only its
branch/minimal ancestors, not siblings. Schema `select: false` is eligible, while
identity/permission metadata and implementation fields retain separate rules.

### Call policy and document-result reuse

One immutable call policy governs fetch planning and output. Each document/scope/access
stage owns separate hook grants and memoized field decisions. Declare projected private
hook inputs (for example `ownerId`) with `alwaysSelectFields`; full document grants resolve
once even with skim or disabled/stripped/limited metadata. `_view`/`_edit` and hook metadata
still describe request permissions, not backend grants.

Successful single results expose `context.documentAuthorization`; lists/create expose one
`contexts[index]` per row. The non-enumerable opaque handle is outside `data` and preserves
owner-dependent `status` and a granted note after `ownerId` and `_permissions` are trimmed.
It accepts only unchanged original or package-created same-stage copies, not caller spreads,
matching IDs, another row/call, or pre-/post-write stage reuse. `getDocumentAuthorization(child)`
looks up an unchanged registered child in the original result graph.

Named `pickAllowedFields`/`trimOutputFields` and `genAllowedFields(..., { purpose: 'output', ... })`
accept either raw **output-only** authorization or the handle, never both. Raw policy is a
fresh evaluation; a recognized trimmed output keeps explicit/unconditional grants but cannot
rerun its hook or recover lost document-dependent decisions. A fresh unassociated input needs
the projected hook inputs. Helpers filter existing values, without selection, virtual getter
execution, restoration, row checks or write authority. Named `genSelect`/`genQuerySelect` return
fresh fetch projections with private inputs, not output grants. Positional `skipChecks`/
`baseFields` overloads remain isolated legacy compatibility APIs.

### Row and related target scope

| Row mode | Effective predicate |
| --- | --- |
| request (default) | transformed ordinary query AND request baseFilter |
| scope | transformed ordinary query AND trusted scope, replacing baseFilter |
| unrestricted | transformed ordinary query, without baseFilter |

Configured `overrideFilter` still runs **once in every mode**, including unrestricted;
its restrictions/false denial remain effective. Trusted scope and mandatory reference/join
constraints are ANDed afterward. Scope is inert (no client `$$sq`/`$$date` expansion); `{}`
means explicit all-row scope within those constraints. Upsert lookup scope does not stamp
values into newly created data. `find.totalCount` and integrated include counts reuse their
effective row scope through private prepared execution.

<!-- doc-example: partial -->

```ts
import type { ModelRequest } from '@web-ts-toolkit/access-router/advanced';
declare const req: ModelRequest;
declare const orderId: string;
declare const tenantId: string;
const service = req.macl.getService<{ customer: string }>('Order');
const result = await service.findOne({ _id: orderId }, {
  select: ['customer'], populate: [{ path: 'customer', select: ['name', 'billingEmail'] }],
}, { authorization: {
  outputFields: { mode: 'grant', paths: ['customer'] },
  related: { customer: {
    model: 'Customer', operation: { mode: 'grant' },
    rows: { mode: 'scope', filter: { tenantId } },
    outputFields: { mode: 'grant', paths: ['billingEmail'] },
  } },
} });
```

The parent grant permits the relationship only. Exact requested populate/include path and
registered target model must match; unused/ambiguous/mismatched entries reject. Child operation,
rows and output authority default independently to request mode, never parent elevation.
Reference IDs, populate match and include joins/filters still constrain all target row modes.
Nested policies belong under the immediate target's `related`; count entries accept only
model/operation/rows. For a subsequent child pick, use its graph handle with **that target's**
service. `$$sq` does not inherit these policies.

Virtual grants permit selected applicable getters and their private dependency fetches; missing
dependencies, undefined or errors can still omit output. Output grants do not authorize writes,
query/sort/distinct fields, database virtual filtering/sorting, rows or target operations implicitly.
Validation, write admission and persistence hooks still apply. Trusted decorate/decorateAll/tasks
run afterward and may construct/remove output; there is no automatic second authorization pass.

### Route entry and service policy

Basic/advanced `operationAccess` guards authorize the generated endpoint before
service dispatch, with HTTP 401 on denial. They replace only its initiating guard.
Direct service calls are trusted application calls and retain their existing
checks; service methods do not universally enforce initiating operationAccess or
infer a transport variant from `req.method`.

Field selection, row/filter policy, validate/prepare/decorate hooks, related-model
checks, and root entry guards remain base-scoped. A permitted variant does not
grant fields or authorize a related target's advanced endpoint policy.
`advancedUpsert` does not additionally require `advancedCreate`/`advancedUpdate`;
its existing create/update branch policy still applies. Root entries keep base
operation names/checks, returning entry 401 inside their HTTP 200 envelope.

### Important behavior

- `_read(id, args, { tryList: true })` and `_readFilter(filter, args, options)` can
  fall back from an authorized read miss to list access, subject to **base `list`**
  operation access. `list: false, advancedList: true` cannot permit retry;
  `list: true, basicList: false` cannot block it. `tryList` defaults to true.
  Forbidden and BadRequest never retry. Denied route entry is distinct from an
  allowed read miss (ordinary 404 when retry is disabled).
- `_update(..., { returningAll: false })` trims the response to the updated fields
- `_upsert(...)` only supports the default `_id` identifier

### Denial versus a missing row

An ordinary false query, false identifier or `rows: { mode: 'scope', filter: false }`
is terminal Forbidden in every row mode, before parsing/identifier/child/persistence work
as applicable. A null/undefined scope predicate is BadRequest; omit row authority for
request-mode behavior. A transform that needs the parsed read/list predicate can deny
before primary persistence, but cannot undo subqueries already needed for parsing.

**Breaking migration:** the complete service `overrides` container (select/filter/populate/
idFilter/effectiveSelect/operation) is removed, including empty/null/undefined or mixed
new/old slots. It now returns actionable BadRequest before parsing/persistence. Use ordinary
select/query/populate plus explicit policy; custom IDs use findOne/updateOne and mutation
select is ordinary. Old object overrides.filter bypassed both filter hooks; new row modes
replace only base scope. Move replaceable user row restrictions into baseFilter when needed;
there is no transform-bypass option. See the package README for every before/after mapping.

Public `_` wrappers, root/HTTP/OpenAPI/client options, defaults, populate and include/`$$sq`
control slots reject authorization and internal/removed controls, including after custom
validator transformations. Legitimate business properties named authorization/overrides
are still ordinary data. The configured `overrideFilter` hook/setter remains supported.

`exists(filter, options?)` applies read row policy by default (`options.access`
changes it). Allowed matches/misses yield successful true/false, or an `{ _id }`
record/null with `includeId: true`. Explicit/base/override false returns a Forbidden
ErrorResult before adapter dispatch in both modes. This replaces the former
successful false/null denial result; check `success` before `data`.

Public reads no longer retry a terminal read denial through list policy. Public
`_upsert` with an `_id` now propagates denied update-policy existence as Forbidden
instead of Unauthorized; an allowed miss remains Unauthorized. Neither case creates
or updates a row. Generated direct routes use HTTP 403 and root batches use entry
403 within HTTP 200. Custom Express handlers own response serialization: returning
an ErrorResult or calling `res.json(result)` does not automatically set status 403.

### Populate access selectors

Wire `options.populateAccess` and populate descriptor `access` accept only
`'list' | 'read'` (`PopulateAccess` from the existing `/advanced` entrypoint).
Related populate/include/subquery checks use target base operations, regardless
of the initiating basic/advanced endpoint.

The shared Core populate boundary rejects all fourteen reserved route-variant
names in effective option and per-descriptor access, including generic legacy
include/subquery options and trusted defaults, before target persistence. Other
trusted non-reserved custom access strings retain their runtime compatibility.
Invalid selectors return controlled BadRequest: direct HTTP 400 or affected root
entry 400/`bad_request` within HTTP 200. Legacy read/list includes now propagate
target BadRequest instead of silently dropping output, so nested invalid selectors
are visible. Existing denial/miss cardinality contracts remain.

### Safe include output and exact counts

Legacy and correlated include `path` values are output-only. They cannot equal,
descend from, or contain the receiving model's `documentPermissionField` (default
`_permissions`). With `auth.policy.permissions`, `auth`, `auth.policy` and
`auth.policy.permissions.canReadSecret` reject; `lineItemCount` or the sibling
`auth.policy.permissionsExtra` do not overlap. Equivalent legacy bracket paths
follow the same rule. The entire supported include tree is preflighted with each
nested receiving model's setting before target persistence. BadRequest returns direct
HTTP 400 or root entry 400/`bad_request` within HTTP 200; malformed reads do not fall
back to list access. Ordinary output collisions remain supported.

Legacy `op: 'count'` uses one grouped aggregate per include execution for all parents,
counting distinct authorized target documents independently of listHardLimit and
include pagination. Duplicate local/foreign array keys or documents matching multiple
local keys do not inflate a parent's count; misses yield zero. The target schema casts
the authorized match (including tenant filters) and foreign operands before/after
unwind, retaining original parent-key association for normalized ObjectId/String keys
and query setters. Invalid casts return controlled BadRequest rather than zero.
Terminal false count row policy retains legacy omitted output; the grouped service
returns Forbidden. Operation denials prevent target work.

Casting does not execute `countDocuments` middleware/plugins or consume a persistence
permit; the aggregate is admitted and runs aggregate middleware. Arbitrary model
aggregate pipelines are not auto-cast. Express count authorization in router operation
and row policies. Correlated counts instead execute per parent through count semantics.

### Nested updates

With only `'profile.public': { update: true }`, send nested JSON
`{ profile: { public: 'New display name' } }`: protected/omitted siblings survive.
This holds for updateOne/updateById, existing-row upsert and single/bulk subdocuments.
Whole-parent grants permit replacement and remove omitted children; whole arrays
replace, while explicit indexed leaf grants patch only that path. Whole grants take
priority over overlapping leaves. Admitted null clears the field; an empty/null client
container supplies no descendant leaves. Literal dotted client keys are ignored by
selection, not interpreted as update operators. See [Hooks](./hooks) for trusted
prepare/transform behavior and its omission compatibility change.

## Correlated Includes

Read/list service paths (`_list`, `_read`, `_readFilter`, and the grouped
root entries that dispatch to them) accept correlated `include` entries
(`mode: 'correlated'`) alongside legacy `localField`/`foreignField` joins.
Each correlated entry runs a target query **per parent document** using
`{ "$parent": "<field>" }` markers resolved against the immediate parent
snapshot:

```json
{ "mode": "correlated", "model": "Org", "op": "read", "path": "org", "id": { "$parent": "orgId" } }
{ "mode": "correlated", "model": "Post", "op": "list", "path": "posts",
  "filter": { "authorId": { "$parent": "_id" } },
  "args": { "select": ["title"], "sort": { "createdAt": -1 }, "limit": 5 } }
{ "mode": "correlated", "model": "Post", "op": "count", "path": "postCount",
  "filter": { "authorId": { "$parent": "_id" } } }
```

Execution notes:

- Reads attach the doc or `null`, lists attach per-parent paginated arrays,
  counts attach numbers (count semantics, never a capped list count).
  Missing/`null` references attach `null`/`[]`/`0` with no target query.
- Identifier reads use the target's configured identifier behavior with no
  read-to-list fallback; counts use explicit count access.
- Dispatch goes through the authorized target service under the active
  request/runtime context. Target denials fail the whole request with zero
  target persistence queries.
- Referenced parent fields are added to the parent DB select, then trimmed
  unless policy-allowed and selected. Sibling include output and
  decorate/task output never feed references.
- Bounds: each entry counts toward `maxIncludeCount`; expanded filters are
  revalidated (`maxNodes`/`maxDepth`/`maxInValues`/`maxLogicalClauses`);
  `maxCorrelatedQueries` (default `100`) caps total inner executions and
  `maxCorrelatedDepth` (default `5`) caps nesting. See [Configuration](./configuration).
- Direct count parents carry no `include`. Malformed correlated input is a
  controlled `BadRequest`, never a silent drop. See [Validation](./validation).

## Data Router Services

`DataRouter.getService(req)` returns a `DataService`.

Methods:

- `find(filter, args?, options?)`
- `findOne(filter, args?, options?)`
- `findById(id, args?, options?)`

## Result Shapes

Service methods return one of these shapes:

- `SingleResult`
- `ListResult`
- `ErrorResult`

List results include `count`, and may include `totalCount` when count support is enabled.
Integrated internal model operations refine successful results to `AuthorizedSingleResult`
or `AuthorizedListResult` with opaque contexts. Public HTTP/root serializers omit context(s),
query diagnostics and private authority; they are not client transport fields.

### Successful subdocument writes with hidden output

Create/single/bulk update response data requires post-save parent read operation/row
access. Full-array create output, including POST `[]`, additionally intersects
`subs.<sub>.list` AND `.read` guards/row filters. Targeted single/bulk updates require
sub read only, not list access. All use read fields plus `_id`; visible counts and
stored array order are preserved. Bulk request order does not reorder the response;
service `addFirst` still governs insertion order, without adding an HTTP option.

These visibility checks use **base** parent/subdocument read/list policy. Disabling
`basicRead`/`basicList` endpoints does not hide otherwise readable mutation output;
allowing an advanced read route does not override a denied base response guard.

A denied response guard, terminal false policy or no readable match hides output
without failing the committed write:

| Operation | Service/root fields (all `success: true`) | Direct HTTP; root entry status |
| --- | --- | --- |
| Create | `kind: 'list', code: 'created', data: [], count: 0` | `[]`, 201; 201 |
| Bulk update | `kind: 'list', code: 'success', data: [], count: 0` | `[]`, 200; 200 |
| Single update | `kind: 'single', code: 'success', data: null` | JSON `null`, 200; 200 |

Root keeps its HTTP 200 envelope. Do not retry successful empty responses. Actual
write denials and validation/persistence failures retain errors. Visibility adds at
most one parent query and resolves applicable row policies once per mutation.

## Permissions Helper

`AccessRouterPermissions` is method-based:

```ts
permissions.has('isAdmin');
permissions.hasAny('posts.read', 'posts.write');
permissions.hasAll(['posts.read', 'posts.write']);
permissions.keys;
```
