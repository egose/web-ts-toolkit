# Hooks

Model and data routers support request-time hooks for ACL decisions, filtering, decoration, and persistence side effects.

## Lifecycle

Model router flow:

- access and query shaping: `operationAccess`, `overrideFilter`, `baseFilter`
- pre-write: `validate`, `prepare`, `transform`
- post-persist: `afterPersist`
- update diff side effects: `onChange`
- delete flow: `beforeDelete`, `afterDelete`
- response shaping: `docPermissions`, `decorate`, `decorateAll`

Data router flow is simpler and mainly uses `operationAccess`, `baseFilter`, `overrideFilter`, `decorate`, and `decorateAll`.

## Common Hook Signatures

All of these hooks run with `this` bound to the current Express request.

### `baseFilter`

Return a filter, or `true` / `null` / `undefined` to leave the query unmodified.
Return `false` for terminal query denial. Model-service `exists` returns Forbidden,
not a successful miss, and public read `tryList` cannot revive that denial.
Integrated internal service row policies use this request scope by default. A trusted
`scope` replaces it; `unrestricted` skips it. Neither changes write-field permissions.

### `overrideFilter`

Rewrite the ordinary filter once before the chosen row scope is applied. This configured
hook/setter remains supported after service `overrides` removal and runs in request, scope
and unrestricted row modes. Its user-dependent restrictions/false denial remain effective;
mandatory relationship constraints and trusted scope are ANDed afterward. An early false
query/identifier/scope skips work as applicable; a later hook denial cannot undo subqueries
already needed to parse a read/list filter. Move replaceable user row restrictions into
`baseFilter` when migrating old object overrides.filter; there is no transform-bypass option.
See [service denial contracts](./services#denial-versus-a-missing-row) for migration,
existence results and HTTP status mapping.

### `validate`

Return `true` to allow the write, `false` to reject it, or an error array to surface validation errors.

### `prepare`

Trusted application hook after validation of selected client data. Output is not
re-filtered and may add protected/server-only fields, including dotted Mongoose paths.
For updates, plain-object/array output at strict ancestors of admitted policy paths
applies supplied children while preserving omitted siblings. Other paths remain whole
assignments. Returning an empty partial container or omitting a parent does not delete
it; explicit null/undefined can clear/unset it. An entirely null/undefined result
supplies no assignments. Do not blindly copy unfiltered `context.originalData` back in.

### `transform`

Mutate the live Mongoose document after authorized update assignment and before save.
For intentional whole-parent replacement use `doc.set('profile', replacement)`.
Migration: prepare hooks that relied on omitted children deleting a partial parent
must now make that replacement explicit here (or grant the client the whole field).
The update order is validation → prepare → assigned-document transform → save →
afterPersist → changes; snapshots/diffs reflect persistence. Subdocument writes retain
their own lifecycle and do not gain these model hooks.

Router lifecycle hooks run outside persistence admission. Mongoose middleware runs
inside its awaited adapter/document operation, which may issue multiple driver
commands; direct DB/network calls from application hooks are not governed by
`maxBulkConcurrency`. See [Configuration](./configuration#persistence-admission).

### `afterPersist`

Run after persistence and before response shaping.

### `beforeDelete` / `afterDelete`

Use these for audit logs, cache invalidation, and external side effects.

### `docPermissions`

Return full request-user document grants from the untrimmed **projected** input. Declare
additional persisted inputs with `alwaysSelectFields` (for example ownerId); the hook does
not implicitly fetch all stored fields. Integrated output resolves it once per document/
scope/access stage independently of skim and permission metadata switches. Pre-write and
post-write output are distinct stages.

Serialization on the configured permission field is separate: disabling/stripping/limiting
metadata does not erase internal grants. Backend output grants do not forge request-user
metadata. Later named output helpers reuse original decisions via the opaque result-context
handle, even after ownerId and metadata trim; a fresh raw policy is new evaluation, not
document-state reuse. See [Services](./services#call-policy-and-document-result-reuse).

### Private populated getter inputs

Package virtuals run after internal document grants and before decoration/tasks.
Their first argument remains an isolated ordinary persisted/local-`dependsOn` view
plus finalized **public** related/embedded outputs. A `dependsOnPopulate` declaration
adds only a separate, declaration-scoped **fourth argument**; it does not retype ref
IDs in argument one or add private maps to `ModelVirtualContext`.

<!-- doc-example: partial -->

```ts
import type { Types } from 'mongoose';
import type { ModelVirtualDescriptor } from '@web-ts-toolkit/access-router';

interface Order {
  total: number;
  account: Types.ObjectId | null;
}
interface Account {
  balance: number;
  creditLimit: number;
}
const canPlaceOrder: ModelVirtualDescriptor<Order, boolean, { account: Account }> = {
  dependsOn: ['total'],
  dependsOnPopulate: [{ path: 'account', select: ['balance', 'creditLimit'] }],
  get(doc, _permissions, _context, populated = {}) {
    const account = populated.account;
    if (doc.total === undefined || account?.balance === undefined || account.creditLimit === undefined)
      return undefined;
    return doc.total <= account.balance + account.creditLimit;
  },
};
```

Assign this separately typed descriptor to ordinary `virtuals` after registering
the target model/options first; see [configuration](./configuration#private-populated-virtual-dependencies).
`ModelVirtualPopulateDependency` and `ModelVirtualPopulateInputs` are available from
root and `/advanced`. The optional third generic explicitly maps source keys to
target persisted shapes; unannotated argument four defaults to an empty type.
It does not select fields or widen persisted, write or public output types.

The runtime always supplies argument four (`{}` without a declaration); the callback
parameter stays optional so existing callbacks and three-argument direct invocations
remain compatible. Default it to `{}` or guard undefined. Known source keys/cardinality
are checked; keys/target fields are optional, scalar targets may be null and source
arrays become readonly arrays of partial targets/null slots (or null). Containers
are deeply readonly/partial. Date/Buffer/BSON keep native types/methods and are cloned
independently per getter, row and repeated slot; readonly containers do not make
native methods immutable or promise equal lean/hydrated materialization.

Only the resolved declaration's paths/mask reach each getter, independently of public
match/select/access. Missing/undefined source refs skip invocation. Present null/empty
arrays invoke with null/[] when private admission/row policy permits; deleted/out-of-scope rows
become null/null slots in original order, preserving duplicates. Missing target fields
remain absent/undefined; present null/false/zero/empty-string survive. The getter chooses
what to return for partial inputs.

The runtime flag `requireOperationAccessForPopulateDependencies` defaults to true.
Only literal false bypasses target base `operationAccess.read` for private loading;
undefined/malformed JavaScript values stay conservative true. Source/target input-field
permissions are already bypassed, but virtual output authorization still governs its result.
Request-mode `overrideFilter.read`, `baseFilter.read` and original source IDs remain mandatory.
False-mode virtual-only output adds no operation check solely for its private fetch.
This server/runtime option is captured before awaits with source/target/query configuration,
including nested output; later calls see changes and runtimes remain isolated. It is not a
caller/query or model option. It is independent of
`requireOperationAccessForPopulateQueries`; actual model registration and an effective
object `permissionSchema` remain mandatory for every target in all four modes.

In true mode target base-read denial, and in both modes terminal false read-row policy,
makes dependencies unavailable and skips affected getters, even for null/empty refs. Dependency-only hook/query/cast errors
omit the virtual with structural-only logs, without raw fallback/retry/new retryable
write errors. Shared ordinary-public query failures keep the ordinary error path.
Invalid configuration fails preflight. Getter undefined/throw and later authorization
denial still reach unconditional public reconstruction/cleanup.

In **all four modes**, private work leaves ordinary ref shape unchanged. The extra
target-base-read reference-visibility gate is removed. Unselected/field-denied source refs
are omitted; otherwise no admitted ordinary population means exact original IDs/arrays
(nulls, missing IDs, ordering, duplicates and presence), including when strict private
admission fails, private rows/queries fail, a getter throws/omits or deferred output
authorization denies it. Admitted ordinary population keeps only its original authorized
mask; admitted misses return scalar null/filtered arrays, not IDs. Query bypass or
list/custom/public related-operation grants cannot be undone by selecting a virtual.
See the [independent policy matrix and migration](./configuration#populate-operation-policies).

There is **no implicit transport** of private maps/raw targets to DTOs, lifecycle
snapshots, public permission hooks/metadata, document handles, or decorate/task input.
Only an authorized getter's deliberate returned value becomes computed output;
mutating inputs alone cannot change another getter, persistence or response fields.
Public related outputs still use target-owned output authority; private terminal
reads use the captured private-read mode and actor's request read-row/tenant scope and
never compute target virtuals. Hydration/native isolation/registration limits are unchanged.

### `decorate` / `decorateAll`

Use these trusted application stages (and tasks) after authorization/finalization. They
can intentionally remove/construct output; no automatic second authorization pass is promised.
Arbitrary replacements/mutations do not acquire valid same-stage document handles.
Private virtual dependency maps have no implicit presence here; returned authorized
virtual values and the reconstructed original public reference shapes do.

## Request Augmentation

Augment the package types when you want custom request fields or permission names:

```ts
import '@web-ts-toolkit/access-router';

declare module '@web-ts-toolkit/access-router' {
  interface AccessRouterPermissionMap {
    isAdmin?: boolean;
  }

  interface AccessRouterRequestExtensions {
    requestId?: string;
  }
}
```

## Guard Helper

`guard(...)` is a route middleware helper.

It accepts:

- a permission string
- a permission string array
- a hook function
- a model condition object

```ts
router.router.get('/admin', guard('isAdmin'), async () => {
  return { ok: true };
});
```

## Permissions Plugin

`permissionsPlugin` adds only a hydrated Mongoose getter alias (default `permissions`)
for existing `_doc[documentPermissionField]` metadata, usually `_permissions`.
It uses active-runtime options, falling back to the default runtime outside managed
execution. It does not compute grants, authenticate an actor or enable field
enforcement; routers/services enforce their policies without the plugin, including
lean results. The alias is separate from package-level computed `virtuals`.

```ts
schema.plugin(permissionsPlugin, {
  modelName: 'User',
  virtualPermissionField: 'permissions',
});
```
